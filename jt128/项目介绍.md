# JT128 现场测试与接入工具包 · 项目介绍

## 一、一句话

给「禾赛 JT128（128 线机械式激光雷达）」从零到上车的一整套现场工具：
**证明雷达是好的 → 量清它的资源占用 → 接进 Gazebo 仿真 → 接进已有导航栈 → 搬到目标机**。
全程**不修改**你已有的机器人项目。

## 二、它为什么存在

| 背景 | 带来的问题 |
|---|---|
| 手上有雷达 + 中文手册 + 厂商上位机（97 MB 的 `.out`），但**驱动要自己从 GitHub 拉**（BSD-3 许可） | 容易把"上位机"当成"驱动"，也不知道该改驱动的哪些配置 |
| 已有一个在跑的导航项目 `cod_-rm2026_-navigation`（RoboMaster 导航栈，原本用 Livox Mid-360） | 换雷达要做适配，但**不能改队友的仓库** |
| 目标机是另一台小电脑（i7 / x86-64 / 有图形界面 / 有 cod 工作区），**没装禾赛驱动** | 需要离线可搬运的部署方案（U 盘不可用时还得能走 GitHub） |
| 雷达数据量极大：双回波 **9000 包/s、82 Mbps、230400 点/帧、5.99 MB/帧** | 引出一连串**非显然**的坑：DDS 大消息、costmap 负载、RViz 卡顿、时间戳单位 |
| 现场（上车/拆车）试错成本高 | 能在桌面上验的，必须提前全验掉 |

## 三、四个真实痛点 → 对应四块能力

| 痛点 | 没有它会怎样 | 项目里的对应 |
|---|---|---|
| 分不清"雷达坏了"还是"我配错了" | 现场瞎试、反复插拔 | **诊断层**：裸 UDP 解析（不依赖 ROS）+ `launch.sh radar` 的启动前五步检查（网卡/IP/代理劫持/探包/才起驱动） |
| 大点云"在发但收不到" | 3.5 帧/s 被误判成雷达坏或 RViz 坏 | **64 MB DDS 共享内存段**（`fastdds_large_msg.xml`）+ 所有入口自动注入 |
| 桌面上无法提前验证"下游能不能吃" | 上车才发现帧名/时钟/负载问题 | **HIL 层**：真雷达点云 → 仿真 costmap；外加硬件无关的回归测试 |
| 换机部署容易漏步骤 | 到现场缺依赖、配置项没生效、路径全错 | **部署层**：依赖自检 + 一键部署 + 沙箱排演 + GitHub/压缩包两种搬运 |

```

├── jt128_verify.sh             一键验收（7 组检查 × 3 种模式）
├── setup_host.sh               配网卡 IP + 链路速率 + ping
├── compat_selftest.sh          适配层回归测试（不需要雷达）

├── launch/                     HIL 启动文件 / 真机 nav 启动文件
├── port/                       依赖自检 / 打包 / 一键部署 / GitHub 分发 / 沙箱排演
└── *.md                        14 篇文档（见第九节，含本篇）

~/hesai_ws/src/                  我为雷达写的两个 C++ 包（不属于 cod，也不属于禾赛）
├── jt128_sim_relay/            真雷达 → 仿真 costmap 的中继

~/HesaiLidar_ROS_2.0/            禾赛官方驱动（BSD-3，我没改源码）

└── launch/jt128_test.py         我加的：只起驱动 + 注入 DDS profile
```

## 五、典型使用旅程

**① 桌面首次验证（约 30 分钟）**
```bash
sudo ~/jt128/launch.sh net enp131s0 192.168.1.100   # 给网卡配雷达网段 IP
./launch.sh radar        # 查网卡→查代理劫持→2 秒裸探包→起驱动
./launch.sh verify       # 话题/频率/点数/frame/丢包/资源
./launch.sh mem          # RSS/CPU/FD/接收队列（判泄漏）
./launch.sh rviz         # 看点云
```
期望：`/lidar_points` 10 Hz、230400 点/帧、丢包 0、RSS 稳定。

**② 数据本身合不合理**
```bash
python3 ~/jt128/pc_stats.py      # 128 条通道是否全在、距离分布、时间戳单位
```

**③ 接进仿真（HIL）**
```bash
jt128sim                                  # 终端2：仿真 + 专用 RViz
jt128hil source:=real start_driver:=false # 终端3：真雷达点云灌进 costmap
python3 ~/jt128/costmap_occ.py            # 占用格变化 = 标记生效
```

**④ 搬到小电脑**
```bash
bash ~/jt128/port/push_to_github.sh --dir ~/jt128_repo --with-driver
git -C ~/jt128_repo push                  # 桌面机：推到自己的仓库
# 小电脑：
git clone -b main <仓库地址> jt128_test && cd jt128_test
./jt128/port/deps_check.sh && ./jt128/port/port_setup.sh "$PWD"
```

**⑤ 接真机导航栈**
```bash
./launch.sh compatcheck   # 先做硬件无关自测
./launch.sh compat        # 起适配层：JT128 → /livox/lidar + /livox/imu + 静态 TF
```

## 六、关键设计决策

1. **绝不改 `cod` 仓库**：需要改行为的地方用"参数文件副本 + launch 参数 + topic remap"实现。
2. **自定位、可整体搬迁**：所有脚本按自身路径定位，路径全可用环境变量覆盖；部署时按目标机重写驱动配置里的绝对路径。
3. **幂等 + 防呆**：重复部署是刷新而非报错；重复起仿真直接拒绝（两个 Gazebo 会互相搞死）；代理劫持/无 IP/无数据包时不启动并给出下一步。
4. **诊断先于集成**：先能"量出来"，再谈"接进去"。所以有 `--selftest`、`compatcheck`、`--diff` 这些不需要硬件就能跑的判据。
5. **结论可复现**：文档里每个数字都配一条能立刻验证的命令（见第七节）。
6. **三层入口**：zsh 函数（最省事）→ `launch.sh <子命令>`（跨 shell）→ 直接 `ros2 launch/run`（最透明）。

## 七、已实测的关键数字（全部来自本机真实运行）

| 维度 | 实测 |
|---|---|
| 链路 | `carrier 1` / **100 Mbps 全双工** |
| 包率 / 带宽 | **8972~9010 包/s / 82.26 Mbps**（手册双回波 82.51） |
| 帧率 / 转速 | **10.0 Hz / 599 RPM** |
| 丢包 | 应用层 **0.00%**；内核 `InErrors 0 / RcvbufErrors 0` |
| 回波模式 | Last&Strongest **双回波**，230400 点/帧 |
| 点云 | `point_step 26`、`ring 0~127`（128 线全在）、距离 0.11~29.13 m（室内） |
| 逐点时间戳 | **单位＝秒**，一帧跨度 100.2 ms，递增比例 1.00 |
| IMU | `/lidar_imu` **406.8 Hz** |
| 驱动资源 | **RSS 222 MB 稳定（90 秒斜率 0.000 MB/min）**、CPU 18.7%（单核）、FD 20 |
| DDS 共享内存段 | **67,133,984 字节（64 MB）**；不注入则点云只有 **3.5 Hz** |
| HIL | `/jt128/points` 9.99 Hz / `front_mid360`；costmap 占据格 **4,237 → 13,117（+8,880）** |
| 适配层 | 输出 `point_step 28`、`tag&0x3F==0`、逐点时间戳 1e8 ns（跨度 100 ms） |

## 八、现状与边界

**已验证**：雷达硬件与链路、驱动功能与内存、点云格式、真雷达 → 仿真 costmap 的通路、适配层输出契约、小电脑部署流程（沙箱排演）。

**未验证**：
- 真机跑 `small_point_lio`（车上的定位效果）——雷达已拔线，且真机还差别的东西；
- loopback 仿真里 STVL 体素层对注入点云不标记（Gazebo 的 obstacle_layer 正常），未定位根因；
- 20 Hz / 单回波工况未实测（要用上位机改雷达参数）。

**边界（别外推结论）**：
- HIL 的**几何是无意义的**：雷达在桌上、机器人在虚拟位置，标出的障碍不代表真实环境 → 只能验"通路"，不能验"定位/避障效果"；
- HIL 不覆盖：串口底盘、真实 TF 外参、LIO 集成。

**已知坑（都写进了对应文档）**：驱动 `ptc_connect_timeout: -1` 会静默卡死（配置已改成 3）；
仿真里两个 Gazebo 会互相搞死（有启动守卫）；大点云不注入 DDS profile 就只有 3.5 Hz；
适配层时间戳单位（已修）；完整缺陷表见 `代码讲解.md` 第 11 节。
