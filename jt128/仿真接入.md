# 真实雷达接入仿真（HIL）使用说明

> ## ⭐ 今天可用的最小验证路径（2026-09-28 实测有效）
>
> **把点云发在 costmap 的全局坐标系里，标记立刻生效。**
> 实测（Gazebo + 我那份把障碍源换成 `/jt128/points` 的参数）：
>
> | 点云 frame | 结果 |
> |---|---|
> | **`odom`**（全局系，圆心放在机器人 odom 位置） | 占据格 **3412 → 8069（+4657）** ✅ |
> | `front_mid360`（仿真雷达帧） | 占据格**完全不变** ❌ |
>
> 说明 `obstacle_layer`、参数、QoS、标记逻辑全都正常，**卡点只在点云坐标系这一环**。
>
> ```zsh
> jt128sim use_rviz:=False        # 1. 起仿真（这份参数把障碍源换成点云）
> # 2. 灌合成点云：发到 odom 系、摆到机器人位置（本机 Gazebo 里 red 车在 odom(-5,3)）
> python3 ~/jt128/sim/jt128_fake_cloud.py --ros-args \
>   -p topic:=/jt128/points -p frame_id:=odom \
>   -p origin_x:=-5.0 -p origin_y:=3.0 -p origin_z:=0.2 \
>   -p points_per_frame:=30000 -p use_sim_time:=true
> # 3. 另开终端验证占据格
> python3 ~/jt128/costmap_occ.py --save /tmp/a.npy
> python3 ~/jt128/costmap_occ.py --diff /tmp/a.npy
> ```
>
> **真雷达为何不能照搬**：真雷达点坐标在雷达自身系里，直接改 `frame_id=odom` 会把几何位置搞错。正确做法是让中继**做 TF 变换**（`tf2_sensor_msgs::doTransform`）+ 配置**安装外参**（真机 URDF 里雷达的安装位姿），而不是只改 frame_id。这是 `jt128_sim_relay` 的下一步改动。

目标：**真雷达的点云喂给 Gazebo 里的导航栈**，不等整车、不占场地，先用真实点云的密度/噪声/视场跑通
`点云 → costmap → MPPI` 这条链路。

## 数据流

```
真雷达 ──UDP──> hesai_ros_driver ──/lidar_points──> jt128_sim_relay (C++)
                                                          │ ① frame_id  front_jt128 -> front_mid360
                                                          │ ② 时间戳    绝对时间 -> 仿真时钟
                                                          │ ③ 可选抽稀   stride / max_points
                                                          v
                                                   /jt128/points ──> 仿真 nav2 local_costmap
                                                                     (observation_sources: points)
```

三个改写都是**必须的**，少一个点云就用不了：

| 改写 | 不改的后果 |
|---|---|
| frame_id → `front_mid360` | 仿真 TF 里没有 `front_jt128`，costmap 报 frame 不存在，点云全丢 |
| 时间戳 → 仿真时钟 | 真雷达时间是绝对时间（SDK 的 `GetMicroTimeU64()`，即主机墙钟），仿真跑的是 `/clock`；TF 变换会报 extrapolation，点云全丢 |
| 抽稀（可选） | 115200 点/帧 ≈ 1.84 MB/帧，costmap 每帧做 TF + 栅格化，nav2 跟不上时会积压 |

## ⚠️ 两个已踩过的坑（都验证过原因）

### 1. Fast DDS 大消息丢包 —— 必须设置 profile

现象：**发布端稳定 10.0 Hz，订阅端（C++ 也一样）只收到 1~2 Hz**。

原因：本机 `net.core.rmem_max = 212992`（208 KB），Fast DDS 默认共享内存段 ≈ 536 KB，
而一帧点云是 1.84 MB —— 两条路都装不下，消息只能退回 UDP 分片重组，大量帧直接丢。

解决：`~/jt128/sim/fastdds_large_msg.xml` 把共享内存段放大到 64 MB。**发布端和接收端都要设**：

```bash
export FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/jt128/sim/fastdds_large_msg.xml
```

- `jt128_sim_hil.launch.py` 里已经用 `SetEnvironmentVariable` 自动设置
- 但**仿真那一侧（Gazebo + nav2）必须你自己在启动前 export**，否则 costmap 收不到
- 验证生效：`ls -la /dev/shm | grep fastrtps` → 段大小应为 **67133984**（约 64 MB）
- 效果对比：设置前 C++ 中继 1~2 帧/s，设置后 **10.0 帧/s 零丢帧**

### 2. Python 中继接不住真雷达

`rclpy` 反序列化 1.8 MB 的 `uint8[]` 是逐元素的，实测 Python 中继只能吃 1~2 帧/s。
所以中继用 **C++** 写（`~/hesai_ws/src/jt128_sim_relay`，colcon build 6 秒）。
`~/jt128/sim/jt128_sim_inject.py` 是同功能的 Python 版，仅留作小数据量/逻辑验证，别拿它跑真雷达。

## 仿真从哪来（一个常见误解）

仿真**不需要**外部 `~/fzsd2025` 工作区：`cod` 仓库里的 `src/fzsd_vendor/` 就带着
`rmu_gazebo_simulator` / `fzsd2025_robot_description` / `pb2025_nav_bringup` / `sdformat_tools`，
并且已经编译进 cod 工作区（实测只 source humble + cod，`ros2 launch cod_sim fzsd_sim_launch.py --show-args` 正常）。
`fzsd_sim_launch.py` 开头写的"前置：source ~/fzsd2025/install/setup.zsh"是**过时的注释**，
两边的 `rmu_gazebo_simulator` 逐文件比对完全一致（只差一个 `.git`）。所以机器人主机上只要有 cod 就够了。

## 启动步骤（3 个终端）

```bash
# 终端 0（一次）：让 zsh 提供 jt128 系列命令
source ~/jt128/jt128.zsh

# 终端 1：仿真（用配套参数把障碍源从 rplidar 的 /scan 换成点云）
export FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/jt128/sim/fastdds_large_msg.xml
jt128sim                     # = ros2 launch cod_sim fzsd_sim_launch.py params_file:=~/jt128/sim/gt_sim_jt128_params.yaml

# 终端 2：真雷达 → 仿真
jt128hil                     # = ros2 launch ~/jt128/launch/jt128_sim_hil.launch.py
#   没接雷达想先干跑（合成房间+柱子点云，链路与真雷达完全一致）：
jt128hil source:=fake

# 终端 3：验证
ros2 topic hz /jt128/points              # 期望 ≈10 Hz（Python 订阅者也能到 10 Hz，说明传输没问题）
ros2 topic echo --once --field header.frame_id /jt128/points   # front_mid360
ros2 topic echo --once --field width /jt128/points             # 115200（单回波）
```

看效果：仿真 RViz 里把 **Local Costmap** 打开，雷达前方应出现真实几何对应的障碍（干跑模式是四面墙 + 正前方 1.5 m 柱子）。
点云里出现的障碍**相对机器人的位置是真实的**：人站在雷达前 1 m，仿真里机器人前方 1 m 就会长出障碍。

## 性能调参

| 参数 | 用途 |
|---|---|
| `stride:=4` | 每 4 点留 1 点（115200 → 28800），nav2 卡顿时用 |
| `max_points:=30000` | 按帧均匀抽到 3 万点 |
| `qos_reliable:=true` | 默认 best-effort；改成 reliable 会被慢订阅者反压（不推荐） |

## HIL 能测什么、不能测什么

**能测**（这正是 HIL 的价值）：
- 真实点云能不能喂进 nav2（字段、frame、时间戳、QoS、带宽、CPU/内存）
- JT128 的点密度/盲区/垂直视场（-4.4°~90.5°，会看到天花板）对 costmap 与 MPPI 的实际影响
- 真实点云特性下的绕障/停障反应：**真车雷达静止、人在雷达前走动** → 仿真里出现位置正确的障碍 → 看 MPPI 是否绕开
- 链路稳定性与资源占用（`jt128mem`）

**不能测**：
- 全局定位/建图正确性 —— 仿真世界是虚拟地图，与你房间不一致，点云里的障碍会和仿真地图冲突
- 真实环境的完整避障路径 —— 仿真里看到的障碍位置只对"相对雷达的几何"为真，不构成一张完整地图

## 现在这份配置没测到的部分

- Gazebo 没实际起过（需要 GPU + 1~2 分钟加载），costmap 实际吃到点云的效果要你跑 `jt128sim` 才能看到
- 测性能前**先让 update-manager / Gazebo / RViz 安静下来**：刚才实测 `update-manager` 单核 98%、load 3.75，
  这种状态下测出来的内存/CPU 数字没有参考价值
