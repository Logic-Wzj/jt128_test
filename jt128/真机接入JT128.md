# 真机接入：JT128 顶替 Mid-360

> 目标：让 JT128 接进 `cod_-rm2026_-navigation` 的真机导航栈，**cod 仓库一行不改**，
> 机器人模型 / TF 树 / costmap / MPPI 轨迹全部照常工作。

## 数据流

```
hesai_ros_driver ──/lidar_points──┐
                                  ├─> jt128_livox_compat ──> /livox/lidar (frame=livox_frame) ─┬─> cpp_lidar_filter ─> /livox/lidar_filtered ─> nav2 (stvl)
                  ──/lidar_imu────┘                        └─> /livox/imu ──────────────────────┴─> small_point_lio ─> /Odometry + TF odom->base_link
                                   ＋ 静态 TF: base_link -> livox_frame（LIO 必需）
```

之后正常启动 `cod_bringup/singlenav_launch.py`：它起的 `cpp_lidar_filter`、`small_point_lio`、
nav2、rviz 全部按原来的话题/帧工作。

## 为什么只要一个适配层（源码依据）

| 消费方要求 | JT128 现状 | 处理 |
|---|---|---|
| LIO 的 `livox_pointcloud2` 适配器按**字段名**读 `x,y,z,tag(u8),timestamp(f64)`，且只收 `tag & 0x3F == 0`（`small_point_lio/src/lidar_adapter/livox_pointcloud2.h:25-37`） | 禾赛点云是 `x,y,z,intensity,ring(u16),timestamp`，**没有 tag** | 适配层补 `tag=0` 与 `line=ring&0xFF` |
| 时间戳按纳秒解释（`*1e-9`） | 禾赛驱动写进 `timestamp` 的**已经是纳秒**（`HesaiLidar_SDK_2.0/libhesai/UdpParser/include/udp1_4_parser.h:477`） | 不用换算 |
| LIO 要 IMU | 驱动自带 `/lidar_imu`（`config.yaml:84,92`，`send_imu_ros: true`） | 转发成 `/livox/imu` |
| LIO 回调先 `lookupTransform(lidar_frame,"base_link")`，拿不到**静默不发里程计**（`small_point_lio_node.cpp:64-69,108-112`） | `base_link→livox_frame` 在 cod 仓库**没有任何节点发布** | 适配层补静态 TF |
| nav2 只认 `/livox/lidar_filtered`（`singlenav2_params.yaml:221,311`） | 不变 | filter 照旧，无需改动 |

## 怎么用

```bash
# 1) 适配层（终端1）：驱动 + 适配 + 静态 TF 一起起
./launch.sh compat start_driver:=true
#    雷达的实际安装位置不为 0 时补上外参（LIO 用它把点云归到 base_link）：
./launch.sh compat start_driver:=true x:=0.05 z:=0.25

# 2) cod 导航栈（终端2）：原样启动
source /opt/ros/humble/setup.zsh && source ~/cod_-rm2026_-navigation/install/setup.zsh
ros2 launch cod_bringup singlenav_launch.py
```

适配层参数（都可从命令行覆盖）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `in_topic` / `out_topic` | `/lidar_points` / `/livox/lidar` | 点云进出 |
| `target_frame` | `livox_frame` | 必须与 `small_point_lio/config/mid360.yaml:6` 的 `lidar_frame` 一致 |
| `relay_imu` / `in_imu_topic` / `out_imu_topic` | true / `/lidar_imu` / `/livox/imu` | IMU 转发 |
| `publish_tf` / `base_frame` / `x,y,z,roll,pitch,yaw` | true / `base_link` / 全 0 | 静态 TF（真机外参填这里） |
| `stamp_offset_ms` | 0 | 真机保持 0（用雷达自己的时间戳）；仿真里可用来回退 |
| `qos_reliable` | false | 见下方"调试注意" |

## 验证清单（按顺序）

```bash
# 1) 点云到没到、格式对不对
ros2 topic hz /livox/lidar                       # 期望 ≈10 Hz
ros2 topic echo --once --field point_step /livox/lidar    # 期望 28（原 26 + tag + line）
ros2 topic echo --once --field header.frame_id /livox/lidar  # livox_frame

# 2) IMU 频率（**决定 LIO 能不能用**）
ros2 topic hz /livox/imu
#    Mid-360 是 200 Hz。明显偏低（如 <100 Hz）LIO 会漂/抖

# 3) TF 链（LIO 的前提）
ros2 run tf2_ros tf2_echo base_link livox_frame

# 4) LIO 有没有输出里程计
ros2 topic hz /Odometry                          # 期望稳定 ≥10 Hz
#    没有的话，先看 3) 的 TF，再看 LIO 日志

# 5) nav2 侧
ros2 topic hz /livox/lidar_filtered
python3 ~/jt128/costmap_occ.py                   # 占据格应随环境变化
```

## 已知风险与回退

1. **IMU 频率不足**（最可能的问题）：JT128 数据尾里带 IMU，但频率手册未写。若 `ros2 topic hz /livox/imu`
   明显低于 100 Hz，LIO 会漂。回退方案：`./launch.sh compat relay_imu:=false`，IMU 仍用 Mid-360
   （点云用 JT128、IMU 用 Mid-360 的混装；注意两者安装位置不同，必要时用 `x/y/z/rpy` 对齐）。
2. **调试时 `ros2 topic echo` / RViz 收不到 `/livox/lidar`**：适配层默认 **best-effort** 发布（匹配 LIO 与
   滤波器的 `SensorDataQoS`）；而 `echo`/RViz 默认 reliable 订阅，两者不兼容。调试时用
   `./launch.sh compat qos_reliable:=true`，或把工具端 QoS 改成 Best Effort。
3. **`livox_frame` 与真机 URDF 不一致**：如果你们 URDF 里雷达帧另有其名，用
   `target_frame:=<实际帧>` + `publish_tf:=false`（由 URDF 提供外参），并同步改
   `small_point_lio/config/mid360.yaml` 的 `lidar_frame`。
4. **LIO 的 odom 速度恒为 0**（`small_point_lio_node.cpp:90-96` 速度赋值被注释掉）——这是既有问题，
   与 JT128 无关，但会影响依赖 odom.twist 的逻辑，接车时留意。
