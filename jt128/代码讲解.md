## 0. 这套东西解决什么问题

**目标**：把一台禾赛 JT128（128 线机械式激光雷达）接到一台机器人主机上，做到
① 能证明雷达硬件本身是好的；② 能量它的内存/CPU/带宽；③ 能接进已有导航栈（RoboMaster `cod` 项目）和 Gazebo 仿真。

**硬约束（决定了整体设计）**：

1. **绝不修改 `cod_-rm2026_-navigation`**（那是队友的项目，改了就说不清了）→ 所有适配都放在 `~/jt128` 里，
   需要换参数就用**参数文件副本**，需要换话题就用**launch 参数/重映射**。
2. **目标机（小电脑）没有禾赛驱动、可能没有网** → 需要一套可整体搬迁、可离线部署的分发机制（`port/`）。
3. **雷达数据量极大**：出厂双回波 9000 包/s、82 Mbps、230400 点/帧、**5.99 MB/帧**。
   这带来三个连锁问题：DDS 大消息、costmap 负载、RViz 卡顿 —— 全篇多处都在处理它。
4. **现场没人帮你**：所有脚本都要幂等、要能自检、要在出错时说清"下一步查什么"。

## 2. 入口层：`launch.sh`（443 行）

### 2.1 为什么是 bash
现场机器可能是最小化安装，bash 一定有；而且它要 `exec ros2 launch`（换成别的解释器会多一层进程，Ctrl-C 语义变糟）。
纯 bash 的另一个好处：小电脑上不是 zsh 也能跑（当时明确要求过）。

### 2.2 自定位与可搬迁（`launch.sh:36-45`）

```bash
SCRIPT_PATH="$(readlink -f "${BASH_SOURCE[0]}" ...)"
JT128_DIR="$(dirname "$SCRIPT_PATH")"          # 以"文件在哪"为准，不写死 ~/jt128
HESAI_WS="${HESAI_WS:-$HOME/hesai_ws}"         # 每个路径都能用环境变量覆盖
HESAI_REPO="${HESAI_REPO:-$HOME/HesaiLidar_ROS_2.0}"
COD_WS="${COD_WS:-$HOME/cod_-rm2026_-navigation}"
HOST_IP="${JT128_HOST_IP:-192.168.1.100}"
RADAR_IP="${JT128_RADAR_IP:-192.168.1.201}"
DDS_PROFILE="${JT128_DDS_PROFILE:-$JT128_DIR/sim/fastdds_large_msg.xml}"
```
——整个目录拷到任何位置、任何机器都能用；测试时也能用环境变量把路径指到沙箱里（`verify_transfer.sh` 就靠这个）。

### 2.3 网卡探测（今天刚改过，`launch.sh:57-80`）

```bash
list_wired() {        # 排除 lo/docker/virbr/veth/br-/无线/Meta(Clash)
detect_iface() {
    1) JT128_IFACE 环境变量
    2) 已经带 192.168.1.x 地址的网卡
    3) 有线网卡里 link 已 up 的（cat /sys/class/net/X/carrier == 1）
    4) 任意有线网卡
    5) 默认路由网卡（兜底）
}
```
**为什么这么排**：笔记本上默认路由常常是**无线网卡**。原来的顺序（默认路由优先）会让 `sudo ./launch.sh net`
把 `192.168.1.100` 配到 WiFi 上 —— 今天真的踩到了（`detect_iface` 返回了 `wlp128s20f3`）。
`cmd_net` 里还加了防呆：自动探测到 `wl*`/`Meta` 就停下，要求显式指定。

### 2.5 `cmd_radar` 的顺序为什么是这样（`launch.sh:299-330`）

```bash
detect_iface                      # 1. 找出该用哪块网卡
case "$addrs" in *192.168.1.*)    # 2. 没有 192.168.1.x 就直接拒绝，并告诉你去跑 sudo ./launch.sh net
ip route get $RADAR_IP            # 3. 命中 "dev Meta" 说明被 Clash TUN 劫持 → 拒绝启动
jt128_check.py --seconds 2        # 4. 2 秒裸探包，收不到就给出物理排查清单（供电/线序/收发交叉）
cmd_driver                        # 5. 前三关都过才起驱动
```
**设计意图**：把"最可能白折腾半小时"的三件事（网卡选错、代理劫持、物理层没通）在启动前一次性挡掉，
并让每一步的失败都自带**下一步该敲什么**。第 4 步用 Python 裸解析而不是 `ros2 topic hz`，
就是为了在 ROS 还没起来、驱动还没编译时也能判断"雷达到底有没有在发"。

### 2.6 `fixpaths`：两个 Python 块（`launch.sh:102-166`）

1. **绝对路径块**：把 `correction_file_path` / `firetimes_path` 改成本机路径。设了三条保护：
   已是目标值就跳过、当前值文件真实存在就不动、目标文件不存在就保持原样。
   （为什么只用 `re.search` 取**第一处**：`correction_file_path` 在 config 里出现 4 次，只有第一个块是 JT128 的。）
2. **JT128 功能项块**：`ros_frame_id→front_jt128`、`ptc_connect_timeout→3`、`multicast_ip_address→""`、
   `channel_fov_filter_path→""`。两个实现细节：
   - 只改**值**、保留行尾注释（`patch_val` 用分组替换）；
   - **幂等**：已经是目标值就打印"已符合要求"而不是重复改写，所以可以反复跑。

   > `ptc_connect_timeout: -1` 是上游默认值，含义是**初始化时无限阻塞等 PTC 连接**（驱动 README 原文）。
   > 雷达 PTC 不通时驱动会静默卡住，现场表现为"驱动起来了但没点云"。这条是必须改的。

### 2.7 防呆与收尾

- `sim_running()`：`pgrep -f "ros2 launch cod_sim"`。`cmd_sim`/`cmd_hil` 都依赖它 ——
  同机两个 Gazebo 会因 gz-transport 端口冲突互相搞死（先起的那个 `/clock` 直接消失），我踩过一次，代价是白查半天。
- `cmd_down` 的 `pkill -f "jt128_sim_rela[y]"` 这种方括号写法，是为了让模式**不匹配自己这条命令行**。
  ⚠️ 但方括号只保护模式本身，如果同一条命令里**别处**出现了裸的 `rviz2` 字面量，照样会自杀（我踩了第 6 次）。
- `set -u` 在 `source /opt/ros/*/setup.bash` 前后要关掉再打开：ROS 的 setup 脚本引用了未绑定变量。

## 3. zsh 层：`jt128.zsh`（203 行）

**为什么单独写一份**：`launch.sh` 每次都要 `cd ~/jt128 && ./launch.sh xxx`，而现场最常做的是
"起仿真 / 起 HIL / 看状态"。zsh 函数把这些变成 `jt128sim`、`jt128hil`。

- `JT128_DIR` 用 `${(%):-%x}` 推导（zsh 取"当前文件路径"的写法）——文件位置优先，
  能纠正 `.zshrc` 里遗留的旧 export，并提示一次。
- `jt128env`：`source` ROS + `hesai_ws` + `cod_ws` 三个工作区，是所有函数的公共前置。
- `jt128sim`：先查有没有仿真在跑（有就拒绝）→ `jt128env` → 注入 `FASTRTPS_DEFAULT_PROFILES_FILE`
  → `ros2 launch cod_sim fzsd_sim_launch.py params_file:=<jt128 版> "$@"`。
- `jt128hil`：没检测到仿真会**警告但仍允许**（因为 fake 干跑不需要仿真），然后起 HIL launch。
- 其余：`jt128up`（驱动+滤波）、`jt128raw`（裸探包）、`jt128verify`、`jt128mem`、`jt128route`、
  `jt128check`、`jt128status`、`jt128down`、`jt128ps`、`jt128dds`（看共享内存段大小）、`jt128simstock`。
- 已挂进 `~/.zshrc`（备份在 `~/.zshrc.bak-jt128-*`）。
- ⚠️ **教训**：给 zsh 用户不能只给 `source xxx/setup.bash` —— colcon 的 `.bash` 版在 zsh 里靠 `BASH_SOURCE`
  推前缀会算错，报 `没有那个文件或目录: .../setup.sh` + `Package 'cod_sim' not found`。必须用 `.zsh` 版本，
  或者干脆用上面的函数。

## 4. 诊断层

### 4.1 `jt128_check.py`（248 行）—— 不依赖 ROS 的"雷达体检"

自己实现 UDP 收包 + 按手册解析 JT128 的包结构：

```python
PKT_LEN = 1100     # UDP 数据长度（以太网帧 1146 = 14 头 + 1100 + 4 FCS）
TAIL_OFF = 1044    # 数据尾在 UDP 内的偏移
DIS_UNIT_MM = 4    # 距离单位固定 4 mm
RETURN_MODE = {0x39: "最后及最强(默认)", 0x3b: "...", ...}
```
- `parse_packet()`：解出块数/回波数/通道数/距离单位/Flags/工厂信息 + 数据尾里的
  工作模式、回波模式、**转速(0.1 RPM)**、UTC、序号、**IMU 温度(0.01 ℃ 有符号)**、加速度/角速度。
- `run()`：按秒聚合成一张表 —— 包/秒、Mbps、帧率、转速、丢包、运行状态、回波模式、最近点、IMU 温度；
  退出时再打印"首包来源 IP / 协议版本 / 通道数 …"。
- `build_selftest_packet()` + `selftest()`：**构造假包**验证解析逻辑，没雷达也能确认代码是对的
  （`jt128_check.py --selftest`）。
- 设计取舍：单文件、零依赖（只用标准库），因为目标机可能什么都没有。
  代价是它只解析**点云包头部**，不做逐点解算 —— 逐点是驱动的事。

### 4.2 `pc_stats.py`（142 行）—— 点云内容深检（今天新写）

订阅一帧 PointCloud2，回答"数据本身合不合理"：
- **字段布局不写死**：用 `np.ndarray(..., buffer=buf, offset=f.offset, strides=(point_step,))`
  按消息里声明的 `fields` 动态取列，所以换驱动版本/换雷达也不会错位。
- 统计：距离 min/中位/p99/max、全零点数、>60 m / <0.5 m 计数、`ring` 覆盖范围与通道数、
  反射率 min/max/mean、逐点时间戳跨度与递增比例。
- `--json` 输出给脚本用。

> 今天用它实测出的关键事实：`ring 0~127`（128 线全到位）、室内中位 2.81 m、
> **`timestamp` 单位是"秒"**（一帧跨度 100.2 ms、递增比例 1.00）—— 这条直接引出第 8 节的缺陷。

### 4.3 `memwatch.py`（257 行）—— 资源与内核缓冲

- `proc_snapshot()`：读 `/proc/PID/status`(VmRSS) + `/proc/PID/stat`(utime/stime→CPU%) + `/proc/PID/fd`(FD 数)。
- `udp_snmp()` / `udp_recvq()`：读 `/proc/net/snmp` 与 `/proc/net/udp`，给出
  **InDatagrams / InErrors / RcvbufErrors** 与 **Recv-Q**（判断"内核收得下吗、应用读得过来吗"）。
- 汇总：RSS 起止与峰值、**内存增长斜率**（判泄漏）、平均 CPU、FD 变化、Recv-Q 峰值，并给出"✅/⚠️"判定。
- **今天修的 bug**：原来 `find_procs` 只按命令行子串取 PID 最大的那个，结果选到了**我自己的后台 shell**
  （它的命令行里含 `hesai_ros_driver` 字样），读出 11.4 MB 的假数据。现在：
  ① 排除自身与所有祖先进程；② 按"可执行名(comm)命中 > 仅命令行命中"+RSS 从大到小排序；
  ③ 多候选时全部列出。所以今天那条 **RSS 222 MB / 斜率 +0.000 MB/min** 才是真的。

### 4.4 `costmap_occ.py`（99 行）

订阅 costmap（默认 `/local_costmap/costmap`），把 `OccupancyGrid` 统计成"占据/空闲/未知 格数"，
`--save` 存 `.npy`、`--diff` 与之前存的对比较 —— 这是判断"点云到底有没有标进代价地图"最硬的证据。
今天正是靠它得到 **4,237 → 13,117（+8,880）** 这个结论。

### 4.5 `setup_host.sh`（68 行）

`sudo ./setup_host.sh <网卡> [IP] [--tcpdump]`：显示 link 速率 → `ip addr add`（不动原有地址）→
ping 雷达（并说明"ping 不通不代表坏，很多固件不回 ICMP"）→ 可选 tcpdump 5 个包。

### 4.6 `jt128_verify.sh`（231 行）

三种模式：`MODE=driver`（纯雷达）/`sim`（HIL）/`real`（真机+滤波），检查 7 组：
进程 → 话题 → 频率 → 点云内容(width/height/frame_id) → 丢包统计 → TF → 资源。
今天加了两处：
- **点云话题自动探测**（`/lidar_points` → `/livox/lidar` → `/jt128/points`），并打印实际用的是哪个
  —— 之前 launch 默认 remap 到 `/livox/lidar`，而这里写死 `/lidar_points`，导致"话题不存在"的误报；
- 自己注入 DDS profile（订阅端不带的话，6 MB 消息只有 3~4 Hz）。

## 5. 部署分发层：`port/`（5 个脚本，882 行）

### 5.1 `deps_check.sh`（159 行）
19 项检查：ROS 发行版、colcon、编译工具、Python 模块、Qt 运行库（上位机要用）、cod 工作区、
`spatio_temporal_voxel_layer`、仿真包等。`have_lib()` 直接查文件而不是 `ldconfig -p`
（后者的缓存经常不全，我踩过）。每条失败都给安装命令。

### 5.2 `make_bundle.sh`（93 行）
`make_bundle.sh [输出目录] [-a]` → `jt128_port_<日期>.tar.gz`。默认**不含** 97 MB 的禾赛上位机
（专有二进制、ARM 机器也跑不了），`-a` 才打进去。排除 `build/install/.git/__pycache__/app/`。
参数校验：`-h/--help`，并拒绝把 `--xxx` 当输出目录。

### 5.3 `port_setup.sh`（226 行）—— 目标机一键部署
6 步，每一步都幂等：
1. 环境自检（调 `deps_check.sh`）
2. **安装/刷新脚本**到 `~/jt128`：已存在就用 `rsync -a --delete`（排除 `app/`）刷新，
   旧版备份到 `~/jt128.bak`，并统一补 `chmod +x`（ZIP 下载会丢可执行位）。
3. 驱动源码：包里有就拷；**没有就从上游克隆**（默认固定 tag `v2.0.12`，3 次重试），
   并校验 SDK 子模块是否在位 —— 缺了就自动 `git submodule update --init --recursive` 补齐
   （克隆中断会留下"有外层、没 SDK"的半成品目录，原来会被误判为"已存在"直接跳过）。
4. **统一走 `launch.sh fixpaths`**（原来是这里自己又写了一份只改路径的代码，
   结果 JT128 功能项在小电脑上从来没被改过 —— 这是我复盘中发现的真问题）。
5. 编译驱动 + 中继 + 兼容层
6. 写 shell 入口（zsh 追加 `source jt128.zsh`，bash 加 `alias jt128`；`.bashrc` 不存在就新建）

### 5.4 `push_to_github.sh`（242 行）—— 不用 U 盘

## 6. 仿真 HIL 层

### 6.1 `jt128_sim_relay`（C++，137 行）

**为什么必须是 C++**：`rclpy` 反序列化 `uint8[]` 是逐元素 Python 对象，1.84 MB 的帧实测只能吃 1~2 帧/s；
真雷达双回波 6 MB/帧会直接堵死。C++ 版实测 10.0 Hz 零丢帧。

三个参数各解决一个问题：
| 参数 | 默认 | 解决什么 |
|---|---|---|
| `target_frame` | `front_mid360` | 真雷达的 `front_jt128` 在仿真 TF 树里不存在，必须换成仿真里有的帧 |
| `stamp_offset_ms` | 100 | 中继用 `now()` 打戳，比 Gazebo 的 TF 快十几毫秒，nav2 会以"外推到未来"为由丢帧，所以要**回退**一点 |
| `stride` / `max_points` | 1 / 0 | 230400 点/帧对 costmap + RViz 太重，可抽稀（代价地图照样能标） |

实现要点：`out_ = *msg` 复用整块数据（一次 memcpy），只改 `header` 和（抽稀时）重排点；
`use_sim_time=true` 时 `now()` 就是仿真时钟，天然对齐。

### 6.2 `launch/jt128_sim_hil.launch.py`（146 行）
- 按自身位置推导 `pkg_root`（整个目录搬到别处也能用）；

### 6.3 `sim/fastdds_large_msg.xml`（51 行）—— **全项目最关键的一个小文件**

<transport_descriptor>
  <transport_id>shm_large</transport_id>
  <segment_size>67108864</segment_size>      <!-- 64 MB，默认只有 ~536 KB -->

**发布端和订阅端都要带这个环境变量**。验证生效：

## 8. 真机适配：`jt128_livox_compat`（C++，219 行）—— 含一个**已发现的缺陷**

**为什么需要它**：`small_point_lio` 的 `lidar_adapter/livox_pointcloud2.h` 写死了四个字段名：
```cpp
PointCloud2ConstIterator<float>   out_x(msg, "x");        // 还有 y、z
PointCloud2ConstIterator<uint8_t> out_tag(msg, "tag");     // 必须有 tag
PointCloud2ConstIterator<double>  out_timestamp(msg, "timestamp");
if ((*out_tag & 0b00111111) == 0) { ... }                  // tag&0x3F==0 才收
new_point.timestamp = *out_timestamp * 1e-9;               // 按纳秒解释
```
而 JT128 驱动给的是 `x,y,z,intensity + ring(uint16) + timestamp(float64)` —— **没有 `tag`**。
于是这个节点在转发时**逐点追加两个字段**：`tag = 0`（满足 `tag&0x3F==0`）、`line = ring 低字节`；
`point_step` 26 → 28。同时把帧改成 `livox_frame`、话题改 `/livox/lidar`，并把 `/lidar_imu` 中继成 `/livox/imu`。

**🔴 缺陷：`timestamp` 没有做单位换算。**
见 `jt128_livox_compat_node.cpp:163-170` —— 追加字段时是 `std::memcpy(dst, src, in_step)` 原样拷贝，
`timestamp` 保持禾赛的**秒**；而 LIO 按 `×1e-9`（纳秒）解释。

**证据链（三段都对得上）**：
1. 实测（`pc_stats.py`）：`/lidar_points` 的 `timestamp` 字段 min=1029.91309、max=1030.013298，
   一帧跨度 **0.1002 s**，且与 `header.stamp=1029` 同量级 → **单位是秒**（雷达上电累计秒）。
   若是纳秒，值应约为 `1.03e12`、帧内跨度应为 `1e8`。
2. LIO（`small_point_lio/src/lidar_adapter/livox_pointcloud2.h:37`）：`new_point.timestamp = *out_timestamp * 1e-9;`
   → 期望**纳秒**。
3. 我写这个节点时留的注释（`jt128_livox_compat_node.cpp:13-14`）说"禾赛驱动写进 timestamp 的已经是纳秒，
   依据是 SDK `udp1_4_parser.h:477` 的 `sensor_timestamp * kMicrosecondToNanosecondInt`" ——
   **这条注释是错的**：那是 SDK 内部 `PtInfo` 的表示，而 ROS 层最终写进消息的
   `LidarPointXYZIRT.timestamp`（`lidar_types.h:74`，double）是秒量级（实测）。

后果：LIO 拿到的逐点时间是 ~1e-6 s 量级（而不是 ~1e9 ns），**帧内时间间隔缩小了 1e9 倍**，
去畸变（motion compensation）必然算错，可能表现为点云拖影/建图漂移，而不是明显报错。

**修法**（待做）：给节点加参数 `timestamp_scale`（默认 `1e9`），在逐点拷贝时把 `timestamp` 字段
读出来乘完再写回；设 `1` 则不改（用于其它输入源）。这样即使将来驱动改了单位，也能用参数适配。

## 10. 贯穿全项目的五条设计原则

1. **自定位、可整体搬迁**：所有脚本用 `BASH_SOURCE` / `${(%):-%x}` 定位自己，
   路径全可用环境变量覆盖；`port_setup.sh` 部署时按目标机重写 `config.yaml` 的绝对路径。
2. **绝不改 `cod`**：需要换行为的地方一律用"参数文件副本 + launch 参数 + remap"。
3. **幂等 + 防呆**：重复部署刷新而非报错、重复起仿真直接拒绝、Clash 劫持/无 IP/无包时**不启动**并给出下一步、
   远端默认分支不一致时提示、`origin` 已存在时改用 `set-url`、无改动时跳过提交。
4. **结论必须可复现**：文档里每个数量级都写了实测来源（9000 包/s、5.99 MB/帧、RSS 222 MB、
   4,237→13,117 格、67133984 字节共享内存段……），并配一个能立刻验证的命令。
5. **三层入口**：zsh 函数（最省事）→ `launch.sh <子命令>`（跨 shell）→ 直接 `ros2 launch/run`（最透明）。
